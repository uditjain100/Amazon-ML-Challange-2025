# Submission Archives

This directory stores packaged prediction files that were uploaded (or prepared for upload) to the Amazon ML Challenge 2025 leaderboard. Treat every archive here as an immutable record of a leaderboard attempt: it should contain everything needed to recreate the submission or explain its performance.

## Contents
The `datavengers_<date>_<run>.zip` files capture different submission iterations. Each archive typically includes:
- `test_out.csv` – predictions generated by a specific pipeline snapshot.
- Optional metadata (run logs, notebooks, README snippets) bundled for reproducibility.

Filenames follow the convention `datavengers_<DD>_<MM>_<YYYY>_<attempt>.zip`, which makes it easy to reconstruct the submission timeline.

## Best Practices
- Preserve every successful submission for auditability and rollback.
- Store a short changelog inside each zip (e.g., `notes.txt`) summarising the features or models used.
- When promoting a submission to production, reference the corresponding zip and the experiment notebook or script that produced it.
- Avoid editing archives in place; instead, generate a new zip whenever the underlying predictions change.

## Packaging Checklist
1. From the `student_resource/` root, run your chosen pipeline (e.g., `python src/clean.py`) and produce `dataset/test_out.csv`.
2. Verify the output locally:
   ```python
   import pandas as pd
   sub = pd.read_csv("student_resource/dataset/test_out.csv")
   ref = pd.read_csv("student_resource/dataset/test.csv", usecols=["sample_id"])
   assert len(sub) == len(ref)
   assert set(sub.columns) == {"sample_id", "price"}
   assert sub["price"].gt(0).all()
   ```
3. Collect supporting artefacts (logs, config snapshots, SHA of the code commit, environment export).
4. Compress the package (still inside `student_resource/`):
   ```bash
   zip -r datavengers_<DD>_<MM>_<YYYY>_<attempt>.zip dataset/test_out.csv notes.txt logs/
   ```
5. Move the archive into this directory and update the table above with a short summary and any links to diagrams or reports in `student_resource/Documentation/`.

## Verification & Upload
- Extract the zip in a temporary location and confirm `test_out.csv` opens without issue before uploading to the leaderboard.
- Re-run the schema checks on the extracted file to catch any packaging corruption.
- Document the public leaderboard score (if available) in `notes.txt` and mirror the value in the table above.
- Once the submission is accepted, notify the team and cross-link the archive with corresponding experiment tracking tools (e.g., spreadsheets, Notion, MLFlow).

## Governance & Record Keeping
- Maintain a mapping between each submission archive and the Git commit or branch used to generate it. Record this mapping inside `notes.txt` or a dedicated metadata file.
- If you retract a submission, keep the archive but annotate the table with the reason (e.g., “Withdrawn: found leakage in features”).
- For leaderboard tracking, append the achieved public score and rank inside the archive notes and in the table above once results are known.
- Coordinate with team members before removing or rewriting archives. The default policy is “append-only”.

## Storage & Version Control
- Large zip files may not belong in regular Git history. Consider Git LFS or an external storage bucket if archives become too large. Keep a lightweight pointer file (e.g., text file with download URL) here if using external storage.
- Ensure filenames remain unique; if re-running on the same day, increment the `<attempt>` number.
- Periodically audit this directory to confirm that each archive still extracts correctly and that checksums match any external backups.

By keeping this README and the archive contents in sync, the team can trace every portal submission back to the exact code, configuration, and documentation that produced it.
